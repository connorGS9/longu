  Searching through the entire code base looking for .y and .l files you won't find any. This is because Rust does its own Lexing and Parsing with the rustc_lexer (stream -> tokens) and the rustc_parser (tokens -> AST) (AST root nodes are structs called Crates)
  Interestingly Rust actually has two lexers though or two parts to lexing: the rustc_lexer which is more low level and doesn't know about Rust's specific meanings and the rustc_parse/src/lexer within the parser package   that enriches those raw tokens for the parser into "wide tokens" actually used for parsing.


2A. Why not use JIT? The alternatives: True Interpreter (Like a Tree-Walker), or Ahead-Of-Time Compilation (AOT S/O Eren Yeager) (EX: Go, Rust, C). 
As I am slowly starting to understand Interpreters like the Tree-Walker that I will make in this codebase are slow because every instruction pays the overhead of being examined and dispatched every single time it runs. But they are simpler and portable and they DO NOT produce machine code.
AOT turns your source code into machine code once before running the program and ships a binary file. Fast at runtime, but the compiling happens at build time, not while running.
JIT however starts off like the tree-walker but also watches the code as it runs and compiles certain "hot-spots" (often used / repeated code) into machine code for native speed for the rest of the run ("on the fly"). And this amazing function (hot-spot -> machine code) of JIT compilation can be the weakness. 
  #1. The JIT has to watch the program run for a while to learn what's hot, then spend time compiling it. If your code is very simple executed in 50 MS for example, that hot spot finding and machine code conversion won't even get the chance to shine because the translation has very little payoff compared to a program like a server that will be running for days, weeks, hours, etc.. For short-lived processes, a plain interpreter or an AOT binary beats a JIT. 
  #2. The JIT also takes some of your memory and compute power in order to run at the same time as the code, so if you were working on a microcontroller, or otherwise resource limited system a JIT may not even be able to acquire the resources it needs. Or result in unpredictable consequences when trying to perform it's hot spot translation.
  #3. Security risks due to writing executable memory - JIT generates machine code into memory and then executes that memory so malicious code could be a serious problem compiling directly into end-user system's memory. (EX: IOS strictly prevents JIT compiling so apps that use a JavaScript engine run in a restricted mode)
