## Question 1
 
> Pick an open source implementation of a language you like. Download the source
> code and poke around in it. Try to find the code that implements the scanner
> and parser. Are they handwritten, or generated using tools like Lex and Yacc?
> (`.l` or `.y` files usually imply the latter.)
 
### Answer
 
I chose the **Rust** compiler, using the source together with the
[rustc dev-guide parser page](https://github.com/rust-lang/rust/blob/main/src/doc/rustc-dev-guide/src/the-parser.md).
 
Searching the entire codebase for `.l` and `.y` files turns up **nothing**. That
is because Rust does its own lexing and parsing by hand rather than generating
them with Lex or Yacc. The two pieces are:
 
- **`rustc_lexer`** turns the character stream into tokens (stream to tokens).
- **`rustc_parse`** turns those tokens into an AST (tokens to AST). The root AST
  nodes are structs called **Crates**.
The parser uses **recursive descent**, a top-down technique. This is the same
approach the book teaches you to write by hand, so recognizing it here connects
the challenge directly to what the book is building toward.
 
> [!NOTE]
> **Interesting wrinkle:** Rust actually has *two* stages of lexing.
> `rustc_lexer` is the low-level one and does not know about Rust's specific
> meanings. It produces thin, raw tokens. Then a second lexer inside
> `rustc_parse/src/lexer` enriches those raw tokens into the "wide tokens" that
> the parser actually consumes.
 
**Verdict:** both the scanner and the parser are handwritten, not generated.

## Question 2
 
> Just-in-time compilation tends to be the fastest way to implement dynamically
> typed languages, but not all of them use it. What reasons are there to not JIT?
 
### Answer
 
To see why you would skip JIT, it helps to line it up against its alternatives: a
**tree-walking interpreter** (like the one built in this book) and
**Ahead-of-Time compilation** (AOT), used by Go, Rust, and C.
 
**Tree-walking interpreter.** Slow, because every instruction pays the overhead of
being examined and dispatched every single time it runs. But it is simpler and
portable, and it does not produce machine code.
 
**AOT.** Turns source code into machine code once, before running, and ships a
binary. Fast at runtime, but the compiling happens at build time rather than while
running.
 
**JIT.** Starts off like the tree-walker, but also watches the code as it runs and
compiles the "hot spots" (frequently used or repeated code) into machine code for
native speed for the rest of the run. This on-the-fly compilation is JIT's great
strength, and it is also the source of its weaknesses.
 
### Reasons not to JIT
 
1. **Warm-up cost on short-lived programs.** The JIT has to watch the program run
   for a while to learn what is hot, then spend time compiling it. If a program
   finishes in 50 milliseconds, that hot-spot detection and compilation never gets
   the chance to pay off, unlike a server that runs for hours, days, or weeks. For
   short-lived processes, a plain interpreter or an AOT binary beats a JIT.
2. **Resource-constrained systems.** The JIT uses memory and compute power to run
   alongside the program. On a microcontroller or another resource-limited system,
   a JIT may not be able to acquire the resources it needs, or it may cause
   unpredictable behavior while trying to perform its hot-spot compilation.
3. **Security risk from executable memory.** A JIT generates machine code into
   memory and then executes that memory. The ability to write new code and run it
   is exactly what many exploits abuse, so some platforms forbid it outright. For
   example, iOS strictly prevents JIT compilation, which is why apps using a
   JavaScript engine run in a restricted mode there.

## Question 3
> Most Lisp implementations that compile to C also contain an interpreter that lets them execute Lisp code on the fly as well. Why?

### Answer

In Lisp code is just data as a List like data structure, so Lisp programs can create and run new code while running (through macros, eval, and the REPL), and forcing all of that through a C compiler (especially Macros which expand so many times during code execution) every time would be far too slow, so these implementations keep an interpreter to run freshly-generated code instantly while the C compiler handles the stable code that needs to run fast. The compiler literally cannot finish compiling without running macro code, so even a program that never touches eval or the REPL still needs the interpreter just to build.
